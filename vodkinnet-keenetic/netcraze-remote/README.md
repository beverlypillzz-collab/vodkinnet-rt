# netcraze-remote

Удалённый доступ к флоту **Keenetic/KNDMS-клонов** (Netcraze GIGA и т.п.)
через свой VPS — без проброса портов, работает даже за CGNAT провайдера.

Отдельная панель от `vodkinnet-owrt-remote` (для OpenWrt-флота): свой Hub,
своя БД, свой процесс Xray на своём порту, свой домен/nginx. Может стоять
на том же VPS рядом с owrt-remote — ничего не пересекается.

## Почему отдельный проект, а не форк OpenWrt-агента

`vodkinnet-owrt-remote` держится на трёх вещах, которых на KNDMS просто нет:

| Механизм в owrt-remote | Почему не работает на Keenetic/KNDMS |
|---|---|
| `uci` (конфиг, `uci get/set`) | UCI — часть OpenWrt, на KNDMS нет |
| `procd` (init-сервис) | procd — часть OpenWrt, на KNDMS нет |
| LuCI (веб-морда, меню) | На KNDMS своя веб-морда NDMS, LuCI нет |

Ядро при этом переносится один в один — сам механизм реверс-туннеля
(Xray VLESS + TLS, клиент сам стучится наружу) не привязан к OpenWrt.
Xray-core на Netcraze уже стоит и работает (для XKeen) — просто
netcraze-remote запускает **свой отдельный процесс** Xray, со своим
конфигом, никак не трогая `/opt/etc/xray/configs/` (конфиги XKeen).

## Важное отличие KNDMS: SSH — это не одна вещь

На OpenWrt SSH — единственный dropbear. На KNDMS SSH-поверхностей может
быть **две принципиально разные**:

1. **SSH самой NDMS** — встроенный SSH-доступ прошивки (то, что описано
   в `netcraze_vpn_setup_summary.md` как способ попасть внутрь после
   установки Entware).
2. **SSH внутри Entware** — отдельный демон (`opkg install openssh-server`
   или dropbear), если он вообще ставился, живёт независимо от (1), обычно
   на другом порту.

netcraze-remote **не гадает**, какой из них нужен, и не считает, что оба
обязательно есть. Вместо жёсткой пары "admin+ssh" (как было в первой
версии) — **произвольный список сервисов** на роутер: любой TCP-порт
локально на устройстве можно превратить в отдельный независимый
реверс-туннель, добавив его кнопкой в панели. По умолчанию при создании
роутера Hub заводит только 2 сервиса (NDMS-морда, SSH NDMS) — второй SSH
(или что угодно ещё) добавляется **вручную, только если он реально есть**.

## Архитектура

```
Keenetic/KNDMS (за CGNAT, без белого IP)
    │  Entware: /opt/sbin/netcraze-remote (агент, plain-конфиг, без uci)
    │  entware_ok() — функциональная проверка перед любым действием
    │  N процессов reverse-соединений в одном xray (по одному на сервис)
    ▼
VPS (свой, с белым IП)
    │  netcraze-remote-xray: слушает VLESS+TLS, "portal" reverse-туннеля
    │  netcraze-remote-hub.py: панель, SQLite, heartbeat API — от НЕ-root
    │  nginx: HTTPS-терминация, отдельный домен
    ▼
Ты открываешь https://<домен>/ → видишь роутер online/offline → на странице
роутера — карточка на КАЖДЫЙ сервис с готовой командой `ssh -L ...`.
```

## Модель доступа: admin + ssh (как у owrt-remote)

У каждого роутера — ровно два реверс-канала (не произвольный список, это
сознательный откат к схеме owrt-remote после ревью — "точная копия"
означает и то же самое количество слотов):

- **admin** (`admin_host:admin_port`, по умолчанию `127.0.0.1:80`) —
  веб-морда NDMS.
- **ssh** (`ssh_host:ssh_port`, по умолчанию `127.0.0.1:22`) — SSH.

Про то, что на KNDMS "SSH" — не всегда одна вещь (см. секцию выше): раз
слот только один, `ssh_host`/`ssh_port` в форме роутера в панели просто
указываются на ТОТ SSH, который реально нужен именно сейчас (SSH самой
NDMS, или отдельный sshd/dropbear внутри Entware, если он есть) —
`install.sh` печатает список реально слушающих портов, чтобы не гадать.

Каждый канал = свой VLESS UUID + свой reverse-tag (детерминированный,
`reverse-{router_id}` и `reverse-{router_id}-ssh` — вычисляется одинаково
и на Hub, и в агенте, не хранится отдельной колонкой БД) + свой
изолированный туннельный порт на VPS (`entry_port`/`ssh_entry_port`,
слушают только `127.0.0.1`, наружу не торчат). `entry_port` указывается
вручную в форме добавления роутера в панели (не назначается автоматически)
— панель проверяет, что порт ещё не занят другим роутером.

После добавления/изменения роутера нужно вручную нажать в панели
**"Обновить Xray CFG"**, затем **"Рестарт Xray VPS"** — авто-рестарта на
каждое изменение нет (как и в оригинальном owrt-remote).

## Безопасность

- Hub и Xray-процесс работают **не от root** — отдельный системный
  пользователь `netcraze-remote`. Единственное root-действие (рестарт
  `netcraze-remote-xray` по кнопкам "Обновить/Рестарт Xray VPS" в панели)
  — через узкое sudoers-правило на один конкретный `systemctl`-вызов.
- Cookie сессии: `HttpOnly; Secure; SameSite=Strict` — с уникальными
  именами (`netcraze_remote_*`), отдельными от cookie owrt-remote (cookie,
  в отличие от localStorage, не разделяются по порту в браузере — при
  одинаковых именах на одном домене сессии двух панелей путались бы).
- Security-заголовки на все ответы (`X-Frame-Options`, `X-Content-Type-Options`,
  `Content-Security-Policy`, `Cache-Control: no-store`).
- SQLite/state-файлы: директории `0700`, файлы `0600`.
- Xray-core скачивается install-vps.sh с проверкой **SHA256-чексуммы**
  релиза (через `.dgst`-файл, не единый `SHA256SUMS`, которого у
  Xray-core просто нет) — если сумма не совпала или недоступна,
  установка прерывается.
- Пароль администратора никогда не передаётся как аргумент командной
  строки (не виден в `ps aux`/истории) — только через переменную
  окружения, лениво подхватываемую при первом обращении к авторизации.
- Certbot deploy-hook чинит права ключа (группа `ssl-cert`) после
  каждого renew и рестартит **только** `netcraze-remote-xray`, не трогая
  другие сертификаты/панели на этом же VPS (проверяет `RENEWED_LINEAGE`).
- TLS на реверс-канале включается по `TLS_CERT`+`TLS_KEY` на Hub. Если
  они не настроены, Hub **не отдаст** `TLS_SNI` в конфиге агента — иначе
  клиент пытался бы TLS, сервер открывал бы `security:none`, и туннель
  бы просто не поднимался без внятной причины в логах.

## Устойчивость (self-healing)

Агент на устройстве не может "просто зайти и перезапустить" сам себя, если
упал xray — тоннель и есть единственный канал доступа. Поэтому
`heartbeat-loop` (крутится постоянно в фоне) на каждой итерации проверяет:

1. `entware_ok()` — функциональная проверка (не просто "opkg есть в PATH"):
   `opkg --version` реально отвечает, `/opt/etc/opkg.conf` существует,
   `/opt` смонтирован **отдельно** от `/` (защита от "флешка физически
   отключилась после старта" — известный сценарий на этой платформе).
2. Если Entware в порядке, но xray-процесс не запущен — **сам поднимает
   его заново**, без вмешательства человека.

`entware_ok()` также гейтит `start`/`doctor`/установку xray-core через
opkg — ничего не пытается работать, если Entware не по-настоящему рабочий
(см. `netcraze_vpn_setup_summary.md`, документированный баг "Entware
числится включённым на диске, но не развёрнут").

## Удаление

### Роутер (Keenetic/KNDMS)

Файл нужно сначала скачать (сам по себе на устройстве он не появится) —
например через wget, как и `install.sh`:

```sh
wget -O uninstall.sh "https://raw.githubusercontent.com/beverlypillzz-collab/vodkinnet-rt/main/vodkinnet-keenetic/netcraze-remote/uninstall.sh"
sh uninstall.sh
```

По умолчанию останавливает агент, удаляет бинарь/init-скрипт/логи, но
**оставляет** `/opt/etc/netcraze-remote/netcraze-remote.conf` (там
секреты — UUID/токены). Чтобы удалить и конфиг тоже:

```sh
PURGE=1 sh uninstall.sh
```

### Hub (VPS)

```sh
sudo sh vps/uninstall-vps.sh
```

Останавливает и удаляет оба systemd-юнита, sudoers-правило, certbot
deploy-hook, nginx-vhost, бинарь Hub-скрипта. По умолчанию **оставляет**
базу роутеров (`/var/lib/netcraze-remote`) и отдельный бинарь Xray
(`/usr/local/bin/netcraze-remote-xray`) — на случай, если переустанавливаешь,
а не насовсем сносишь. Флаги:

```sh
PURGE=1 sudo sh vps/uninstall-vps.sh          # + стереть базу роутеров/логины
REMOVE_XRAY=1 sudo sh vps/uninstall-vps.sh    # + удалить бинарь Xray
REMOVE_USER=1 sudo sh vps/uninstall-vps.sh    # + удалить системного пользователя netcraze-remote
```

Все три флага можно комбинировать (например
`PURGE=1 REMOVE_XRAY=1 REMOVE_USER=1 sudo sh vps/uninstall-vps.sh` —
полная зачистка без следа). Сертификат Let's Encrypt при этом **не**
удаляется — если домен общий с другой панелью (см. секцию про общий
домен ниже), трогать его руками отдельно от netcraze-remote не нужно.

## Установка

### 1. VPS — Hub

```sh
curl -fsSL "https://raw.githubusercontent.com/beverlypillzz-collab/vodkinnet-rt/main/vodkinnet-keenetic/netcraze-remote/vps/install-vps.sh?v=$(date +%s)" | sudo sh
```

Спросит домен, выпустит сертификат, создаст системного пользователя
`netcraze-remote`, поставит отдельный бинарь Xray с проверкой checksum,
настроит sudoers-правило, certbot deploy-hook, и напечатает пароль
администратора один раз.

> Обычная для `curl | sh` схемы оговорка: скрипт тянет код из ветки `main`
> публичного репозитория. Для продакшн-инсталляций разумно закрепиться на
> конкретном коммите/тэге вместо `main`, если это важно для модели угроз.

### 2. Keenetic/KNDMS — агент

Сначала должен быть настроен Entware (см. `netcraze_vpn_setup_summary.md`
в базе знаний — раздел про Entware/OPKG на этой прошивке).

```sh
wget -O - "https://raw.githubusercontent.com/beverlypillzz-collab/vodkinnet-rt/main/vodkinnet-keenetic/netcraze-remote/install.sh?v=$(date +%s)" | sh
```

Скрипт сам проверит, что Entware реально работает (не просто "числится"),
и покажет список реально слушающих локальных портов (чтобы понять, есть
ли отдельный SSH внутри Entware помимо SSH самой NDMS).

Дальше:
1. В панели Hub → "Добавить роутер" → название (создаст 2 дефолтных сервиса).
2. Если нужен второй SSH (Entware) или что-то ещё — "+ Добавить сервис"
   на странице роутера, используя порты из списка, который показал install.sh.
3. Скопируй блок конфига целиком (кнопка "Копировать").
4. Вставь в `/opt/etc/netcraze-remote/netcraze-remote.conf` на Keenetic
   (проще всего через SMB-шару Entware).
5. `/opt/etc/init.d/S99netcraze-remote start`
6. `netcraze-remote doctor` — диагностика.

## Что сознательно НЕ сделано (см. "На горизонте")

- **Веб-прокси до NDMS внутри панели** (как LuCI-прокси в owrt-remote) —
  вместо этого команда `ssh -L`. Причина: NDMS отдаёт HTML с абсолютными
  путями, path-based проксирование требует переписывания HTML на лету и
  легко ломается на JS-запросах/абсолютных URL.
- **SSH-терминал в браузере** — то же самое: `ssh -p <порт> root@127.0.0.1`
  прямо с VPS, где и так есть shell.
- Push-уведомления — есть в owrt-remote, не портированы.

## Мини-шпаргалка команд

| Где | Команда | Что делает |
|---|---|---|
| Keenetic | `netcraze-remote status` | статус агента + список сервисов |
| Keenetic | `netcraze-remote doctor` | диагностика (entware/xray/heartbeat/сервисы) |
| Keenetic | `netcraze-remote pull-config` | перетянуть актуальный конфиг с Hub целиком |
| VPS | `systemctl status netcraze-remote-hub` | статус панели |
| VPS | `systemctl status netcraze-remote-xray` | статус reverse-туннеля |
| VPS | `curl -sS http://127.0.0.1:8099/health` | healthcheck панели |

## На горизонте

- Веб-прокси до NDMS в самой панели (если ssh -L окажется неудобным)
- Регистрация роутера с самого агента (первичное добавление всё ещё
  делает админ руками в панели — осознанно, чтобы флот нельзя было
  пополнить извне без доступа к панели)
- Учёт нескольких VPS/панелей в одном общем дашборде, если флот вырастет
- Закрепление install-скриптов на конкретном git-коммите вместо `main`

## Changelog

### 2026-07-29 — фикс проверки checksum Xray-core
При первом реальном запуске `install-vps.sh` на боевом VPS упал на
`curl: (22) 404` при попытке скачать `SHA256SUMS` — у Xray-core такого
файла на релиз **не существует**. Сверено с официальным
`XTLS/Xray-install/install-release.sh`: там для каждого конкретного
ассета качается свой файл `<имя_ассета>.dgst` с полями
`MD5=`/`SHA1=`/`SHA2-256=`/`SHA2-512=`, а не общий SHA256SUMS.
Исправлено в `install-vps.sh`: теперь качается `${XRAY_ASSET}.dgst`,
хэш достаётся через `awk -F'= ' '/256=/{print $2}'`. Проверено вживую на
реальном релизе (`Xray-linux-64.zip` + `.dgst`, суммы совпали).

### 2026-07-29 — обход кэша CDN для файлов проекта (не только install-vps.sh)
На практике всплыло: `raw.githubusercontent.com` (Fastly) кэширует по
эджам, привязанным к сети запроса — с одной машины CDN уже отдаёт свежий
файл, с другой (VPS) ещё старый, и кэш-бастинг `?v=$(date +%s)` не всегда
это лечит. Проблема была не только в самом `install-vps.sh` (это решается
`git clone` вместо `curl|sh`), но и **внутри** него — скрипт сам тянет
`hub.py`, sudoers, certbot-hook, systemd-юниты через `curl` с того же CDN,
и мог бы молча (без ошибки) подсунуть старые версии.
Добавлена функция `fetch_file()`: если `install-vps.sh` запущен как
реальный файл из локального git-клона (`git clone` + `sh install-vps.sh`,
не `curl|sh`), все сопутствующие файлы берутся напрямую из того же клона
рядом со скриптом, минуя CDN полностью. Классический `curl|sh` как фолбэк
не тронут. Проверено: детект локального клона и фолбэк на CDN при
отсутствии реального пути скрипта — оба сценария протестированы.

### 2026-07-29 — поддержка общего домена с другой панелью (напр. owrt-remote)
Запрошено: возможность использовать тот же домен, что уже занят другой
панелью (owrt-remote) на 443, просто на другом внешнем порту — сертификат
одного домена спокойно обслуживает несколько портов, а вот два nginx
server-блока с одинаковым `server_name`+`listen 443` конфликтовали бы.
`install-vps.sh` теперь отдельно спрашивает внешний HTTPS-порт (Enter=443).
Если домен и порт совпадают с уже существующим сертификатом — новый
certonly не запрашивается, существующий переиспользуется. Если порт не
443 — редирект-блок `listen 80 -> 443` для этого домена не создаётся
(чтобы не задваивать redirect, который уже наверняка есть у другой
панели на этом домене). ufw открывает именно выбранный внешний порт.
Итоговый URL панели в выводе показывает порт, только если он не 443.
Проверено генерацией обоих вариантов nginx-конфига (443 и нестандартный
порт) — оба валидны.

### 2026-07-29 — фикс зависания на polkit + nginx reload vs restart
На реальном прогоне (общий домен с owrt-remote) всплыли два новых бага:

1. Самый первый вызов `regen-xray` (пишет xray.json ДО того, как
   `install-vps.sh` ещё успел создать systemd-юнит `netcraze-remote-xray`)
   пытался всё равно вызвать `systemctl restart` этого несуществующего
   юнита. Юнита ещё физически нет, а `netcraze-remote` — не root, поэтому
   `systemctl` уходил в интерактивный polkit-промпт
   (`AUTHENTICATING FOR org.freedesktop.systemd1.manage-units`, предлагал
   выбрать identity среди `overlord`/`chester`/`admin-rt`), зависал и падал
   по таймауту 15 сек. Итоговое сообщение при этом ЛОЖНО утверждало
   "перезапущен", хотя рестарт провалился.
   **Исправлено**: `regenerate_xray_config_and_reload()` теперь проверяет
   `Path("/etc/systemd/system/<service>.service").exists()` и просто
   пропускает попытку рестарта (без polkit-промпта, без таймаута), если
   юнита ещё нет — конфиг при этом всё равно записывается. Сообщение в
   `regen-xray` больше не утверждает успех, если он не подтверждён.
   Проверено тестом: юнит отсутствует -> конфиг пишется, рестарт
   корректно пропущен с явным логом, без обращения к systemctl вообще.

2. `nginx -t && systemctl reload nginx` падал с `nginx.service is not
   active, cannot reload` — nginx на сервере оказался не запущен ещё до
   прогона скрипта (по причинам, не связанным с этим кодом — ветка
   stop/start nginx для certbot вообще не выполнялась, т.к. сертификат
   уже существовал от owrt-remote). `reload` не работает на остановленном
   сервисе. **Исправлено**: `systemctl restart nginx` вместо `reload` —
   корректно и стартует, и рестартует независимо от текущего состояния.

### 2026-07-29 — тот же polkit-промпт вернулся на повторном прогоне
Фикс из предыдущего пункта проверял только "юнит ещё не существует" — но
на ПОВТОРНОМ прогоне `install-vps.sh` (переустановка/обновление) юнит с
прошлого раза уже есть, а ранний bootstrap-вызов `regen-xray` всё ещё
передавал `NETCRAZE_REMOTE_SUDO_RESTART=0`, что означало "звони systemctl
без sudo" — и голый systemctl от непривилегированного `netcraze-remote`
опять уходил в интерактивный polkit-промпт и висел.
**Исправлено**: добавлен отдельный явный флаг `NETCRAZE_REMOTE_SKIP_RESTART=1`
— means "не трогай systemctl вообще, ни с sudo, ни без", приоритетнее
проверки существования юнита. `install-vps.sh` для самого раннего
bootstrap-вызова теперь использует именно его вместо `SUDO_RESTART=0`.
Проверено тестом: флаг работает даже когда указано имя реально
существующего юнита и `SUDO_RESTART=1` одновременно выставлен — restart
не вызывается в любом случае.

### 2026-07-29 — конфликт порта с owrt-remote + ранняя проверка порта
На реальном прогоне выбранный внешний HTTPS-порт (8443) оказался уже
занят **собственным Xray VLESS-портом owrt-remote** (не осиротевший
nginx, как можно было подумать по сообщению об ошибке — `ss -tlnp`
показал `*:8443` держит процесс `xray`, отдельный от netcraze-remote).
Ошибка всплывала только в самом конце `install-vps.sh` (bind-конфликт
nginx), когда уже почти всё было установлено — плюс `set -eu` в тот
момент обрывал скрипт целиком, не давая дойти до финального вывода
логина/пароля.
**Исправлено**: сразу после вопроса про внешний порт скрипт проверяет
`ss -ltn` на занятость этого порта и сразу и понятно останавливается,
если порт занят — не тратя время на весь остальной цикл установки.
Паттерн детекта проверен на реальном формате вывода `ss` (без ложных
срабатываний вида "8443 совпал с 18443").

### 2026-07-30 — крупный перенос: точная копия owrt-remote вместо упрощённой реализации
По замечанию: обе панели должны быть идентичны функциями и внешним видом,
отличаться — только взаимодействием с ОС. Полностью переписано:

- **Hub** — теперь прямой перенос `owrt-remote-hub.py` (5000+ строк:
  дашборд, метрики, SSH-терминал в браузере, авторизация/сессии, кнопки
  Xray reload/restart, push-уведомления). Заменено только то, что реально
  завязано на ОС: хранение конфига (`uci set` → обычный shell
  `KEY="value"` файл). Схема БД не менялась — уже была OS-агностична.
- **Порты разведены** с owrt-remote (чтобы не конфликтовать на одном
  VPS): VLESS 8443→8444, внутренний HTTP 8088→8099, конфиг Xray —
  в отдельную `/etc/netcraze-remote/`.
- **Найден и исправлен реальный баг с именами cookie**: `SESSION_COOKIE`/
  `ROUTER_COOKIE` у обеих панелей назывались одинаково — а cookies (в
  отличие от localStorage) не разделяются по порту в браузере, сессии
  между панелями на одном домене путались бы. Переименовано в
  `netcraze_remote_*`.
- **Оформление**: оранжево-голубая тема вместо оранжево-красной,
  укороченный баннер `NETCRAZE · RT HUB`, перекрашенные favicon и
  иконка-робот на карточках.
- **Агент** переписан почти один-в-один с owrt-remote: те же имена полей
  в heartbeat JSON (панель рендерит метрики без единой правки на своей
  стороне), тот же детект Xray через `/proc/*/cmdline` вместо
  самоуправляемого pidfile (надёжнее — переживает внешний
  рестарт/ручной запуск). Поверх — Keenetic-специфика:
  `entware_ok()` (функциональная проверка, не просто "opkg есть в PATH"),
  generic-пробы модели/LAN-IP без привязки к сборке, watchdog в
  heartbeat-loop.

**КРИТИЧЕСКИЙ БАГ, найденный при переносе**: `make_openwrt_config()`
(теперь `make_router_conf()`) брал `reverse_tag`/`ssh_reverse_tag` из
колонок БД роутера — а `make_server_xray_config()` реально вычисляет tag
детерминированно как `reverse-{router_id}`, эту колонку вообще не читая.
Для новых роутеров колонка БД по умолчанию — буквально `"reverse-in"`
независимо от id, значит для любого роутера, кроме случайно совпавшего,
tag в клиентском конфиге НЕ совпадал бы с тем, что слушает сервер — и
реверс-туннель тихо не поднимался бы, при этом heartbeat (отдельный,
прямой HTTP-запрос роутер→Hub, к туннелю отношения не имеющий) продолжал
бы бодро репортить роутер как онлайн. **Этот же баг один в один
присутствует и в оригинальном owrt-remote** — стоит проверить отдельно,
там же не трогал. Исправлено: `make_router_conf()` теперь вычисляет tag
той же детерминированной формулой. Проверено тестом на 2 роутерах — до
фикса теги совпадали бы у обоих (конфликт), после фикса — уникальны и
совпадают между client- и server-конфигом.

`doctor` дополнен живой проверкой: генерирует client-конфиг, валидирует
JSON, прогоняет через `xray -test` — должно точно показать причину, если
Xray на реальном устройстве всё же не стартует, вместо тихого падения.

### 2026-07-30 — 502 Bad Gateway: несовместимость CLI после переноса
Причина 502: `install-vps.sh` вызывал команды, которых у портированного
Hub'а просто нет — `set-admin-password`/`regen-xray` из старой версии,
а у owrt-remote CLI называется иначе (`set-login`, `render-xray`).
Бутстрап-шаги установки падали молча, Hub либо не стартовал, либо не
получал логин — nginx корректно поднимался, но проксировать было не на
что.

Исправлено:
- `init` (с ленивой авто-инициализацией логина через переменные
  окружения `NETCRAZE_REMOTE_ADMIN_USER/PASSWORD`) вместо
  `set-admin-password` — так пароль не светится в `ps aux`, поскольку
  `set-login` требует `--password` явным обязательным флагом.
- `render-xray --out ... --listen-port ...` вместо `regen-xray` — просто
  пишет файл, не трогает systemctl вообще.
- Найдены и исправлены испорченные слепой заменой пути: `RAW_REPO_BASE`
  указывал на несуществующий `.../Vodkinnet-RT/main/vodkinnet-netcraze-remote`
  вместо `.../vodkinnet-rt/main/vodkinnet-keenetic/netcraze-remote`;
  такая же опечатка в ссылке на GitHub в шапке.
- `reload_vps_xray()`/`restart_vps_xray()` (кнопки «Обновить Xray CFG»/
  «Рестарт Xray VPS») в оригинале owrt-remote зовут `systemctl` напрямую
  без sudo — это требовало бы полного root для всего Hub'а, что свело
  бы на нет всю работу по непривилегированному пользователю. Обе функции
  патчены на `sudo -n` (та же узкая sudoers-запись).
- Инструкции в конце install-vps.sh обновлены: `entry_port` теперь
  вводится вручную в форме добавления роутера (не назначается
  автоматически), и после изменения списка роутеров нужно руками
  нажать «Обновить Xray CFG» → «Рестарт Xray VPS» — авто-рестарта на
  каждое изменение (как было в старой версии) в портированном коде нет.

Проверено: `init` и `render-xray` реально выполнены end-to-end на
одноразовом state dir, оба работают.

### 2026-07-30 — критический фикс: read из stdin ломался при curl|sudo sh
На практике введённый домен раз за разом оказывался обрывком текста
error-сообщений самого скрипта (`[!!] домен 'мер 'р' вместо 'p').'...`).
Причина: при `curl ... | sudo sh` shell-процесс читает ИСХОДНЫЙ КОД
скрипта из stdin, и любой `read` внутри скрипта конкурирует за тот же
поток — вместо того, что печатает человек в терминале, `read` подхватывал
следующие строки СОБСТВЕННОГО ИСХОДНОГО КОДА скрипта. Классическая
проблема интерактивного `read` в связке с `curl | sh`.
**Исправлено**: оба `read` (домен, внешний порт) теперь читают явно из
`/dev/tty`, в обход stdin. Добавлена проверка доступности `/dev/tty` с
понятной ошибкой вместо непонятного краша, если скрипт всё же запущен
полностью неинтерактивно.
